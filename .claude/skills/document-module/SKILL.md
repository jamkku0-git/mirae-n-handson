# 레거시 모듈 문서화

분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로)의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다. `vendor/` 는 열지 않는다(grep 은 `--exclude-dir=vendor`).

## 모듈명
`<모듈명>` 은 폴더 이름이 아니라 아래 표의 값이다. 표에 없으면 사용자에게 묻는다.

| 모듈 경로 | 모듈명 |
|---|---|
| legacy/item-bank-php | item-bank |
| legacy/assignment-thymeleaf | assignment |
| legacy/grade-mssql | grade |

## 절차
각 단계가 끝나면 결과를 파일로 저장하고 다음 단계로 넘어간다. 범위 제한이 있으면 그 범위만 다룬다.

1. **계획 제시**: 읽을 파일 · 단계 · 산출물을 먼저 보여 주고 사용자 확인을 받는다.
2. **진입점**: 라우트 · 컨트롤러 · 화면 · 배치 · 프로시저를 찾는다. → `docs/<모듈명>/ARCHITECTURE.md` 에 저장.
3. **의존 관계**: 진입점에서 호출 방향(누가 누구를 부르는가)과 외부 의존(DB · 파일 · 라이브러리)을 정리한다. → 같은 파일에 추가.
4. **데이터 흐름**: 요청 → 처리 → 저장 · 조회 경로와 테이블 관계를 정리한다. → `docs/<모듈명>/ERD.md` (Mermaid `erDiagram`).
5. **비즈니스 규칙 후보**: 조건문 · SQL · 검증 코드에서 규칙을 뽑는다. → `docs/<모듈명>/BUSINESS-RULES.md`.
6. **표본 점검 추천**: 사람이 직접 확인할 규칙 3개를 추천한다. 가장 그럴듯해 보이는 규칙 1개를 반드시 포함하고, 나머지는 확신도가 낮거나 여러 파일에 걸친 규칙으로 고른다. 이유를 한 줄씩 적는다.

## 규칙 형식
```
### BR-01 규칙 이름
- 규칙: 한 문장. 코드가 실제로 하는 일만 쓴다.
- 근거: `파일:줄번호` (여러 개면 쉼표로)
- 근거 코드:
  ```
  실제 코드를 그대로 인용
  ```
- 확신도: 확실(조건문 · SQL 로 확인) | 추정(이름 · 주석으로 짐작)
- 비고: 예외 · 오류 문구 · 중복 정의 등 (없으면 "없음")
```
- 근거를 찾지 못하면 규칙으로 올리지 않고 "확인 필요"로 따로 모은다. 주석에만 있는 내용도 마찬가지다.

## 하지 말 것
(`docs/item-bank/BUSINESS-RULES.md` 에 "검증 이력" 절이 없어 실제 오류 사례는 없다. 표본이 모두 통과했다는 뜻이므로 아래는 예방 문장이다.)
- 존재하지 않는 함수 · 클래스 · 테이블 · 컬럼을 근거로 쓰지 않는다. 이름을 적기 전에 grep 으로 정의를 확인한다.
- 호출 방향을 뒤집지 않는다. A 가 B 를 부르는지 B 가 A 를 부르는지 호출 지점의 `파일:줄번호` 로 확인한다.
- 코드에 없는 규칙을 만들어 내지 않는다. 일반적인 관례("보통 이렇게 한다")나 주석 · 이름만으로 규칙을 확정하지 않는다.
- 인용한 코드와 줄번호를 기억으로 쓰지 않는다. 저장 직전에 해당 줄을 다시 읽어 일치하는지 본다.
- 없는 기능(예: 수정 · 삭제)은 "없다"고 쓰고 그 근거(grep 결과)를 적는다.
- 실제로 실행해 보지 않은 동작을 "실행 확인"이라고 쓰지 않는다.
